# 模块六：反馈与持续修改（`session_feedback`）

产品链路最后一环（产品总体需求 §4.6/§9）：首轮剪辑完成后，用户用自然语言
持续修改——"第二个爱心小一点""把爱心删掉""音乐换一个""撤销"。

模块六是**会话编排层**，不写新的剪辑语义：把"用户反馈 → IntentPatch →
局部重规划 → 素材重解析 → Executor Diff"串成闭环，并维护 turn 级会话状态
与 Undo/Redo。上游五个模块的接缝全部复用：

```
            ┌─────────────────── FeedbackSession ───────────────────┐
 video ────→│ start: VU.analyze ║ parse(initial) → 增量查询           │
            │        → plan → resolve_assets → materialize → apply  │
            │                                                      │
 utterance →│ reply: meta 拦截 → bridge 视图 → parse(patch)          │
            │        → patch_flow 归一化 → apply_patch(intent)       │
            │        → replan → 增量素材 → materialize → apply      │
            │                                                      │
  撤销/重做 →│ undo/redo: 快照三件套 + apply(旧 resolved)            │
            └──────────────────────────────────────────────────────┘
```

依赖方向：`session_feedback` 单向依赖 gesture_intent / video_understanding /
editing_planner / asset_manager / edit_executor，无反向。

## Session 状态布局

与上游共享 `workspace/<pid>/`（semantic_video_state.json / asset_registry.json /
execution/ 都在同一项目目录），模块六只占 `session/` 子目录：

```
workspace/<pid>/session/
├── session_state.json    # project_id/turn/queries_seen/undo_stack/redo_stack
├── intent/               # IntentStore（state.json + history.jsonl）
├── plan/                 # planner.save → logical_editing_plan.json
├── resolved_plan.json    # 最近一次成功 apply 的 ResolvedEditingPlan
├── turns.jsonl           # TurnRecord 追加审计日志
└── snapshots/snap_NNNN/  # undo 快照：{intent,plan,resolved}.json（model_dump 深拷贝）
```

`queries_seen` 是正确性关键：累积下发过模块二的归一化查询，之后每次
`build_semantic_view(queries=…)` 必传——否则 `query_statuses` 为空，已分析但
无结果的事件会被 replan 误判为 not_analyzed → 假 dependency。

## 首轮 `start(video, utterance)`

```
vu.analyze_video(video)                          # 模块二：语义状态落盘
║ parser.parse(initial)                          # 模块一：EditingIntent
                                                 # （两者互不依赖，线程并行）
→ vu.resolve_queries(required_video_queries)     # 增量分析 + queries_seen 累积
→ build_semantic_view(queries=queries_seen)      # planner 吃 SemanticView
→ planner.plan(intent, view, …)                  # 模块三：LogicalEditingPlan
→ asset_mgr.resolve_assets(plan.asset_requests)  # 模块四：BindingRecord[]
→ planner.materialize(深拷贝 plan, bindings)     # ResolvedEditingPlan
→ executor.build_input → executor.apply          # 模块五：rev_0001 提交
→ 落盘三件套 + TurnRecord                        # start 不入 undo 栈
```

`materialize`/`apply_patch` 原地改 plan——快照与落盘只存 `model_dump`
深拷贝（`_copy_plan`），防止污染 undo 快照。

## 反馈轮 `reply(utterance, dry_run=False)`

```
meta.classify(utterance)          # 在 parser 之前拦截会话命令
    ├─ 撤销/undo   → undo()
    ├─ 重做/redo   → redo()
    └─ "换一个"    → switch fast-path（见下）
→ bridge.build_project_view(edit_view, resolved_plan, intent)
      # EditView 对象翻成模块一 SemanticProjectObject（引用解析桥）
→ parser.parse(current_intent, project_view, video_view=as_intent_view)
      # patch 模式：IntentPatch + unresolved + required_video_queries
→ vu.resolve_queries(patch.required_video_queries)   # 增量分析
→ patch_flow.normalize_patch(patch, unresolved, intent, plan_items)
→ IntentStateManager.apply_patch(intent, patch)      # intent 是真相源
→ planner.replan(plan, new_intent, patch, view)      # 局部 PlanPatch
      # plan() 只收到 scoped intent（changed 需求 + 目标落在 scope 内的
      # 持久 op + music 需求，约束全量随行）——Creative LLM 不再每轮
      # 为全量需求重创作
→ asset_mgr.resolve_assets(patch 新增/变更请求)       # 只下发增量
→ planner.materialize(深拷贝, 全部 bindings)
      # bindings 由 binding_mgr.active_for + search_history 重建，不做快照
→ executor.apply / dry_run
→ 成功才：快照入 undo 栈、清 redo、turn+1、落盘三件套、TurnRecord
```

结束态端到端判定：执行结果 `completed/completed_noop → applied`、
`dry_run → preview`、`needs_dependency → needs_clarification`、其余 →
`failed`；patch 归一化后为空时，有 unresolved → `needs_clarification`
（不并入 intent，不留垃圾 op），无 unresolved → `no_change`。

### bridge：EditView → SemanticProjectView

模块一 `_resolve_raw_target` 按 id 精确命中 / 关键词+序号 / 候选列表三级
解析，桥接层把可编辑对象翻成它吃的形态：

- `id = source_plan_item_uid`（`pln_xxx`）：解析出的 object_id 在 planner
  `_resolve_target_items` 的 by_uid 分支直接命中，不走 display_id 模糊匹配；
- `object_type`/`description` 反查 source requirement——EditView 的
  object_type 是语义类（music 对象显示 "audio"），不是模块一枚举；
- `event_ref` = 事件绑定需求的 `trigger.event.canonical`：resolver 靠它决定
  删整绑定（无序号）还是删单实例（"第二个"）；
- `order` = 同需求内按 `project_time.start` 排序——"第 N 个"的序号基准；
- `aliases` = [display_id, semantic_label, role, object_type, object_uid]。

### patch_flow 归一化（四步，顺序敏感）

先翻译再 `apply_patch`——intent 始终是真相源，规则抽取器的 IdAllocator
续编号只产新 id，不归一会出现重复需求：

1. **replace→update**：`add_object_requirements` 中 action=replace 且 intent
   已有同 object_type 的单例语义需求（music/background）→ 改写进
   `update_*_requirements` 沿用旧 req id → plan_item_uid 稳定 → executor
   走 `replace_media` 就地替换（"音乐换一个更欢快的"）；
2. **歧义坍塌**：unresolved remove 的全部候选对象共享同一
   `source_requirement_ids[0]` → 路由到 `remove_*_requirement_ids`——
   "把爱心删掉"且只有一个爱心绑定时删整绑定，而非误报歧义；
3. **实例删除翻译**：`remove_object_requirement_ids` 中的 `pln_*` 实例 id ——
   源需求已删 → 丢弃；源需求仍在 → 转成 `ExplicitOperation(remove,
   target=object_id=pln_xxx)` 沉淀进 intent，后续 replan 不复活该实例；
4. **unresolved op 剔除**：add/update_operations 里 target 仍为
   object_reference 的 op 不并入 intent——否则每轮残留 op 产
   unsupported plan item 刷 warning。

## "换一个" fast-path（meta 层，必经）

规则抽取器对"换一个/再来一个"产出空 patch（无新描述可抽）——必须在
parse 之前拦截：

```
"音乐换一个" → switch_target_phrase 剥句尾换资源动词
  → resolve_switch_target（复用模块一 _candidate_objects + _ordinal）
  → plan item.asset_request_ref
  → asset_mgr.switch_alternative(request_uid)
      # 候选池切换（Binding.alternatives），不重搜——同 query 重搜
      # 必命中同一首选造成 noop
  → materialize（新 binding）→ executor.apply → diff 出 replace_media
  → 快照 + 落盘，status=switched
```

- "海星换成椰子树"（`换成/替换成/改成` 等新描述）**不拦截**，走正常 parse；
- 无备选 → `needs_clarification`（reason: no alternative candidate）；
- 目标歧义 → `needs_clarification` + candidates；
- executor.apply 非 completed → `failed`，不写 resolved_plan/快照——
  apply 失败时 committed graph 未动，磁盘态仍一致。

## Undo / Redo（turn 级，git-revert 式前进）

每次成功 apply **之前**快照 `{intent, logical_plan, resolved_plan}`（model_dump
深拷贝）压 `undo_stack`；undo = 弹栈恢复三件套 + `executor.apply(旧 resolved)`
——executor 的 desired-graph diff 自动产出反向操作（DELETE↔CREATE、
replace_media 换回旧 asset），**revision 单调前进**，不存在"回滚 revision"；
当前态同时压 `redo_stack`。新编辑清 redo。栈空 → `nothing_to_undo` /
`nothing_to_redo`。`start` 不入栈——首轮即撤销返回 nothing_to_undo。

## 对上游模块的最小改动

### 模块三（editing_planner）

1. `api.py` `_items_for_operations`：`OperationType.remove` 解析到已有
   PlanItem → 直接剔除该项（实例级删除）；未解析 → 维持
   `remove_segment + unsupported`；
2. `api.py` `_items_for_object_requirements`：mutation 类 op
   （scale/position/volume/replace_music）不塞
   `target={"type":"video","value":"main_video"}`——否则 executor 按
   target 解析会把 asset_uid 覆写到主视频对象；留空走 role 默认分支；
3. `replan/patch.py`：依附型 op（scale/position/replace_text/remove）常驻
   intent.explicit_operations——已被 `adjusted_by:{op.id}` 标记或当前
   无可解析目标时不视为变更，否则每个持久 op 每轮强制全量 replan；
   约束变更沿 `cstr:<id>:<hash>` provenance 判定，新增约束按适用面找宿主；
4. `_apply_adjust` 在 item.provenance 写 `adjusted_by:{op.id}`（附
   scale_factor 0.8 / 1.25 系数与幂等判定的依据）。

### 模块五（edit_executor）

`diff/properties.py` `replace_media` 的 arguments 补 `asset_uid`、
`backends/memory.py` 应用时同写——此前 op 只改 `media_ref`，而
`asset_uid` 在 fingerprint 内，backend_verify 指纹比对必然失败，
素材替换路径整体不可用。

## FeedbackResult / 状态码

| status | 含义 |
|---|---|
| `applied` | 反馈已并入 intent 并成功提交新 revision |
| `preview` | dry_run 预览——零副作用，无快照/turn/落盘 |
| `switched` | "换一个" fast-path 候选池切换成功 |
| `needs_clarification` | 有未解析引用/无备选——intent 不动，附 candidates |
| `no_change` | patch 为空且无 unresolved |
| `undone` / `redone` | 撤销/重做完成 |
| `nothing_to_undo` / `nothing_to_redo` | 栈空 |
| `failed` | 解析/执行失败（附 message/errors） |

返回携带：parser 摘要（request_type/parser_mode）、plan_patch 计数、
asset_status、ExecutionResult、edit_view、unresolved、三级 dependencies
（planner/asset/executor）、patch_flow notes、warnings。

## Python API

```python
from session_feedback import FeedbackSession, FeedbackStatus

session = FeedbackSession("workspace", "p1")          # 自动装配五个上游模块
r = session.start("video.mp4", "每次比心时出现粉色爱心，加一段欢快的音乐")
```

`executor` / `tool_capabilities` / `accessibility_profile` 均为构造参数。

## 会话恢复与已知限制

- **跨进程恢复**：`session_state.json` + intent/plan/resolved 三件套 +
  execution/ 均在磁盘——新 `FeedbackSession(workspace, pid)` 直接接管，
  undo 快照同样可跨进程用（`tests/feedback/test_session_resume`）；
- **`VideoUnderstanding.load` 丢 `_video_input`**：会话恢复后 on-demand
  手部补跑（hand landmarks 缺失重试）不可用，其余已物化事件/快照/
  查询记录完好——已知限制，需 VU 侧支持后解除；
- **资产绑定不做快照**：`binding_mgr.active_for` + `search_history.jsonl`
  可随时重建；undo 只回 intent/plan/resolved，素材 registry 不回滚
  （素材层是 append-only，绑定切换天然可重放）。
